# PCAO-F practice implementation specification

## Scope and status

This is an independent React practice app with optional Supabase accounts for completed-report backup. Writable attempts live in the visitor's browser. The approved flow has a start page, timed exam page, review-and-submit dialog, and results page with expandable question reviews. The app implements the data and attempt foundation, shared responsive primitives, and all four approved views.

All new-exam actions open a "Choose exam difficulty" dialog before creating an attempt. The user-approved UI offers Advanced and Intermediate. Advanced uses the original reviewed bank; Intermediate uses the uploaded, validated `public/easy-question-bank.json`. Both levels are enabled, and Intermediate is selected by default.

Advanced uses the reviewed version 1.1.0 file. Intermediate uses the reviewed Easy bank version 1.0.0, independently validated against the same app contract. It passed the app validator and retains every stem, option, selection count, and primary domain from the supplied draft; the separate correction report documents its answer review. Synthetic content remains only under `tests/fixtures/`. New attempts require a complete validated bank. Preserve the approved wording, tables, quotations, option order, corrected Q23 and Q24, and unchanged Q45.

## Settings and history routes

React Router provides `/history` for device and signed-in account history, and `/settings` for account settings. Header navigation uses real links; Home retains its history preview. Direct links and reloads keep these URLs. Settings shows session-loading or sign-in/configuration guidance until authenticated, then account controls appear at the same URL. Sign-out replaces Settings with History and clears private report access. Authentication dialogs, session storage and guest-report migration remain shared above the route content.

Home, Exam and Results retain the root URL. Browser history contains only the view and a saved-attempt pointer; Back/Forward revalidates the stored snapshot and ownership. Missing, private or unavailable reports fall back to History; submitted attempts cannot reopen as editable exams. Cloud reports require a matching currently loaded owner-bound report or readable owned device record. Report URLs are outside this change.

In-app navigation, including Back/Forward, out of an active unexpired exam uses the Leave exam confirmation. Cancelling stays at the current entry; confirming proceeds while preserving the deadline, answers, flags and position. Native reload/external-navigation warnings remain separate. Route headings receive navigation focus, and analytics recognizes History independently. Vercel rewrites for both routes and trailing-slash variants serve the app entry after deployment.

## Runtime data contract

`public/question-bank.json` (Advanced) and `public/easy-question-bank.json` (Intermediate) are fetched independently at runtime. It contains `schemaVersion` (currently 1), stable `examId`, publisher `version`, `title`, `durationMinutes` (120), `expectedQuestionCount` (60), `contentStatus` (`pending`, `synthetic`, or `reviewed`), ordered `domains`, and ordered `questions`. Domain objects have stable `id`, `title`, and `expectedQuestionCount`. Exact domain counts are D1=8, D2=13, D3=7, D4=10, D5=7, D6=9, D7=6.

Each question has a stable `id`, `primaryDomain`, `selectionCount`, `stemMarkdown`, ordered `options` with stable `id` and `textMarkdown`, `correctOptionIds`, `explanationMarkdown`, `optionExplanations` keyed by every option ID, and at least one `sources` item with `courseTitle`, `sectionHeading`, and optional absolute `url`. Render stable option IDs as visible labels and preserve the supplied Markdown text and array order. Publish a new dataset version when any question, key, explanation, or source changes.

The validator checks required fields, duplicate IDs, known domain references, option IDs, selection counts, answer cardinality, question count and domain totals. Only `contentStatus: "reviewed"` is allowed for real attempts. The loading and error states explain unavailable data. Markdown uses GFM tables and fenced code blocks. Raw HTML is not executed. Wide tables scroll in labelled, keyboard-focusable containers.

Editing a local JSON file does not update the public app. An updated file becomes public only when a build containing it is deployed.

## Attempts and scoring

Browser mutations run under one origin-scoped Web Lock covering attempt records and their shared history index. New records begin at revision 0; each answer, flag, navigation edit, or submission advances the revision. Older records without a revision remain readable and use revision 0 for their next edit, without migrating snapshots or grades. Saves reject stale revisions, changes to submitted records, and edits to records replaced in another tab. Storage events synchronize other tabs to saved answers or the submitted report; rejected edits load the latest record and explain how to retry. Browsers without Web Locks disable new attempts and cannot resume writable attempts; saved reports remain readable.

Answer controls show pending selections immediately while acquiring the lock, then reconcile with the committed record on success, conflict, or failure. Existing indexed attempts use a single record write and do not rewrite the history index. Adding a record to history restores successful writes if a later write fails; restoration failures show an explicit recovery message. The browser keeps its committed attempt separate from pending answer feedback so submission grades only saved selections.

Recovered start, deadline, and submission timestamps must represent valid JavaScript dates. Submission cannot precede the start, and its reason must agree with whether the deadline had elapsed. Unfinished records cannot contain submission metadata or grades. New attempts reject invalid start/deadline dates, and manual submission after a backward system-clock adjustment records at least the start time. A time-expired submission is only valid at or after the deadline.

Deadline monitoring covers saved unfinished attempts on Start as well as the Exam and its dialogs. Expiry closes replacement confirmation and opens the saved report even when the user has not clicked Resume. Starting a new exam finalizes expired records before deciding which unexpired attempts need abandonment confirmation, preserving expired reports. An expiry operation queued behind a new start cannot pull the user out of the newer attempt.

An attempt stores its ID, start and fixed deadline timestamps, status, current question, answers keyed by question ID, flags, dataset version, and a frozen copy of the validated bank. Submitted attempts additionally store submission timestamp, reason (manual or time expired), and a grading result calculated from their saved selections and snapshot. Recovery validates saved grading results; older submitted records without a stored result still grade from their frozen snapshot. Browser storage recovery validates the saved snapshot and rejects damaged records. Existing attempts use their snapshots for answering, grading, and later review; updated public data is only used by new attempts.

Before submission, the only answer states are Answered (exact required cardinality) and Unanswered (zero or fewer than required selections). The Exam counter, review grid and confirmation use the shared selection-status helper. Flags and current-question markers remain independent. The persistent Exam bar counts a question as answered only when it has exactly the required number of options selected, regardless of correctness. Radio choices can be cleared; checkbox choices can be deselected and cannot exceed the required maximum. Answers, flags, and position save immediately. Domain labels, explanations, and sources stay hidden during the exam.

During an unfinished, unexpired attempt, browser reload and navigation request the native leave confirmation where supported. Attempt history from the Exam opens a keyboard-accessible “Leave exam?” dialog explaining that time continues; cancelling preserves the view and restores focus. Confirming opens history with a visible timer-running reminder. Submission and expiry remove leave warnings, and expiry also closes the leave dialog.

Remaining time is computed from the fixed deadline. The clock refreshes on interval, visibility, window focus, and page-show events and continues through review and attempt history. Reopening the app automatically finalizes expired saved attempts through the shared idempotent submission helper and opens Results. An edit at the deadline triggers the same finalization without changing recorded answers. Question navigation focuses the question heading. Timer updates do not announce every tick or remount Markdown tables. A question earns one point only when the chosen option IDs exactly match the correct set, independent of order. Blank, partial, and incorrect selections earn zero. Practice score is Math.round((correct / total) * 1000). Practice Passed/Failed uses the unrounded comparison correct * 1000 >= 720 * total. Results headline the score out of 1000, a green Passed or red Failed text badge, and “Passing score: 720 / 1000.” Correct/total and overall percentage are secondary; domain percentages remain. The concise note is “Practice score uses equal-weight question scoring; it is not an official certification score.” History derives the same values from each original snapshot and correct count, without migrating stored grades. Submission is idempotent, including after browser recovery.

Results classifies blanks as unanswered and nonblank nonexact sets as incorrect, including fewer than required selections. The three result counts partition 60 questions. Time used is saved start-to-submission time capped at the deadline. All seven domains show snapshot-based correct/total counts and percentages. Practice priorities list up to three domains below 100%, ordered by unrounded percentages with ties following snapshot order.

Results filters are All, Incorrect, Unanswered and Flagged. Native question disclosures start collapsed and show original IDs, exact frozen Markdown, selected and correct sets, reviewed overall and option explanations, and supplied course titles, exact section headings and links. Selected-correct, selected-incorrect and missed-correct options have text, symbols and colour; there is no separate incomplete-selection badge or category. Selected and correct options remain visible. No runtime explanations or readiness assessments are generated.

## Home source courses and submission confirmation

A visible “Source courses” button near the introduction opens “Courses used for this mock.” A domain helper deduplicates validated question sources by course title and URL pair, retaining first occurrence order and returning only these course-level fields. The reviewed bank produces ten linked courses from 100 references. No question content, section-level references, domains, keys or explanations appear in the drawer.

Introduction: “These practice questions were independently written using concepts from the courses below. Individual question references are available after submission.” This does not imply copied scenarios, official questions or proven correctness.

Use a right-side desktop panel and full-width narrow-mobile panel. Reuse modal focus trapping, initial heading focus, Close, Escape and opener restoration; provide backdrop dismissal where a backdrop is visible. Keep the heading and Close reachable while the body scrolls. Label course links by title, with safe new-tab rel attributes. Show loading and unavailable-bank states with retry. Opening or closing the drawer does not create an attempt, start a timer or change history.

Confirmation shows one consolidated unanswered count and explains that this includes questions without the required number of selections when the count is positive. When it is zero, show “All questions have the required number of selections.” instead of outstanding-answer guidance. It also reminds students about any flagged questions, including answered ones. Only the modal countdown is visible during review, submission confirmation, or the leave dialog; the background header countdown is concealed until returning to the exam. Deliberate submission remains allowed. Checkbox limits, exact-number instructions and the neutral selection counter remain unchanged.

## Difficulty selection and bank identity

The Start exam, Start another exam and Results Start new attempt actions share one preparation dialog. Its selection step has an accessible radio group styled as a segmented Intermediate/Advanced toggle, selected-level comparison bullets, validated exam facts and Cancel/Start actions. The selection button reads "Start Exam" for either difficulty, with "Starting exam…" while saving. Default to Intermediate on each opening, including after cancelling an Advanced selection. The toggle adapts to enlarged text by stacking when two labels cannot fit. Opening, toggling and cancellation do not create attempts, write selections to browser storage or start a new deadline.

`src/domain/difficulty.ts` maps Advanced to `public/question-bank.json` and Intermediate to `public/easy-question-bank.json`, with both catalog entries available. Each reviewed bank must validate independently before its Start action is enabled. Both load at startup; the Start page is Ready when either is ready and reports failures by level. Per-level caches deduplicate requests, and a failed bank cannot block the other ready bank. Never substitute banks across difficulties. The original Advanced and supplied Intermediate content/hashes remain unchanged. Each bank has 60 questions, 120 minutes and the prescribed domain totals.

Selection precedes the existing abandonment confirmation. A validated selected bank is required before entering that step. Keep the chosen level throughout replacement; "Keep unfinished attempt" returns to selection, while Close/Escape dismiss the preparation flow. Existing deadlines continue and a reminder is visible. Expiry closes either preparation step and follows shared finalization. Repeated starts, cross-tab revision checks, stale confirmation protection, failed-write rollback and expired-report preservation remain mandatory. Saving disables preparation controls until the locked operation finishes. After a successful new or replacement start, capture and cancel multi-click continuation events before they activate controls in the new Exam view. A fresh single click or keyboard activation releases this guard immediately; no fixed input-delay timer is introduced. The new attempt must remain answer-free until deliberate input.

New saved attempts include optional `difficulty: "intermediate" | "advanced"` metadata alongside their original frozen snapshots. Recovery validates the enum; saving an existing attempt rejects changes to its difficulty. Edits, resume and submission retain it. Exam, Results and history display the saved level. Older records lacking metadata display "Original exam" without modifying their snapshots or scores. Resume and Open report bypass the selector.

The Source courses drawer shows one shared course list for Intermediate and Advanced, with no difficulty toggle or level-specific heading. It derives the list from a ready validated bank, preferring Advanced when both are ready and using Intermediate when Advanced is unavailable. If neither is ready, show loading while either bank loads, otherwise an error/retry or unavailable state. Retry requests both banks independently. This presentation does not substitute banks when starting an exam. Both levels share ten course title/URL pairs (Advanced: 100 references; Intermediate: 70). The user-approved difficulty comparison has three bullets per level, covering reading load, interacting constraints and structured evidence. Intermediate: "Shorter, more focused scenarios.", "Fewer interacting constraints per decision.", "More compact tables and supporting evidence." Advanced: "Longer scenarios with more details to track.", "More interacting constraints and tradeoffs.", "More detailed tables, records, and supporting evidence." Test fixtures remain outside runtime data. The supplied title "Independent PCAO-F Practice — Easy" is preserved in the bank and frozen snapshots. For attempts saved with Intermediate difficulty, the Exam header, Results and PDF reports display that title as "Independent PCAO-F Practice — Intermediate" through the shared presentation helper. Other titles and records without difficulty metadata retain their saved title.

## Optional account history

Account preferences and account management live on a dedicated Account settings page, available from the signed-in header. Home lists device/account reports and backup feedback; Results contains report-specific actions. Settings navigation from an unfinished Exam uses the existing leave confirmation, saved answers/flags and original continuing deadline. Settings has a focusable page heading and a Back to attempt history action. Signing out closes Settings and returns Home. The trusted-device-copy choice is shared between Settings and Home report opening, and resets for account changes. Bulk device-history import and account-history JSON export are removed. Individual completed reports can be exported as PDFs from Results. Dedicated settings navigation, heading focus, guarded entry from an active Exam and return/resume were verified in real Chrome on 2026-10-16. See REAL_BROWSER_QA_2026-10-16.md for remaining coverage gaps.

Email/password signup and sign-in are the only account identifiers; email confirmation is disabled. Signup requires a complete multi-label domain, valid ASCII mailbox/domain syntax (IDNA domains may use xn-- labels), a maximum 64-character local part and a maximum 254-character address. Matching database validation guards direct Auth signup and changed emails; unchanged legacy accounts remain usable. This does not verify DNS, delivery or mailbox ownership. Authentication dialogs remain dismissible during submission; cancellation aborts/fences late session responses, and requests/body reads time out after 30 seconds with retry guidance and retained form fields. Account UI is enabled only when VITE_ACCOUNT_HISTORY_ENABLED=true and a valid Supabase URL/publishable key are configured. Guests retain the existing exam flow. The migration and three account functions are deployed; hosted HTTP/SDK authentication, backup/recovery, owner isolation and deletion checks pass. Production frontend rollout, SMTP and restore verification remain pending. Sign-in and Create account controls sit at the right side of the shared header on Start, Exam and Results, with responsive wrapping and focus-managed authentication/recovery dialogs.

Password recovery setup resumed on 2026-10-15 with owner-supplied Gmail SMTP and production redirect screenshots. Local implementation adds a tab-scoped pending marker bound to the SDK account/session, a Finish password reset action after dismissal, restoration on reload, safe callback failure/resend UI and auth URL cleanup. No URL flag or marker grants authentication. The marker clears on completion/sign-out/explicit login or account/session mismatch. TypeScript, 46 focused helper/error/cancellation unit checks, all seven synthetic recovery browser cases and the production build pass after explicit owner approval. The owner subsequently requested recovery as a normal account feature. It is enabled by default for configured accounts; only VITE_PASSWORD_RECOVERY_ENABLED=false disables it. The normal local configuration is enabled, and the recovery browser configuration no longer forces a test-only enable flag. Actual hosted delivery/reset/login remains unverified. See PASSWORD_RECOVERY_RESUME_STATUS.md. While disabled, hide Forgot password, show “Password recovery is currently unavailable. Please keep your password safe.” in sign-in/signup, reject recovery requests/password updates in the hook and do not open the new-password dialog from recovery events. Retain the implementation for later SMTP/callback setup and authorized verification; the frontend gate does not disable Supabase APIs themselves. Changes require a rebuild/redeploy on Vercel.

When enabled, password recovery requests use actionable error messages with allowlisted provider codes and valid HTTP status references. Raw provider messages and account-existence codes are not displayed. Restricted email delivery, disabled email authentication, rejected addresses, rate limits, timeouts and connectivity/service errors have distinct guidance. An unconfigured client fails explicitly rather than returning false success. Accepted requests show conditional requested-link copy without guaranteeing delivery or confirming account existence. Public recovery requires custom SMTP and an allowed callback URL; the owner confirmed SMTP is not enabled on 2026-10-15. The local diagnostic change is unverified and does not configure hosted email delivery.

With “Keep me signed in on this device” unchecked, authentication tokens use sessionStorage and survive reloads within the same tab’s browser session. Checked sessions use localStorage for persistence beyond that session. A sessionStorage preference preserves the tab’s selected mode when another tab changes the device preference. Changing mode migrates the current token and clears its old stored copies; token refresh uses the selected store. Sign-out clears sessionStorage, localStorage and memory session copies. Cancelled authentication requests retain the existing session-write fence. If sessionStorage is blocked, unchecked sign-in falls back to memory and cannot survive a reload. Real Chrome checks on 2026-10-16 verified an unchecked session surviving same-tab reload, sign-out hiding private reports, and checked login restoring in another same-origin tab. Blocked-storage fallback and browser restart were not exercised; see REAL_BROWSER_QA_2026-10-16.md.

New accounts enable automatic backup during signup, whether or not completed guest reports exist. This preference binds future new attempts to the signed-in account through separate immutable ownership markers; users may turn it off in Account settings, and sign-in preserves existing choices. The initial account-preference read cannot overwrite signup initialization. If saving this preference fails, show an actionable warning and still prepare guest-report migration. Successful signup automatically claims and queues valid, unowned completed browser reports independently of the automatic-backup preference, including legacy records. Existing browser report bytes are preserved. With no completed guest history, the account starts with no report rows or placeholder attempts. Unfinished, already-owned, paused/deleted and unreadable records are excluded; readable reports continue when an individual record fails. Ownership is persisted under the existing Web Lock before queue creation, so retries/reopening recover interrupted migration. Account history loads automatically after signup or sign-in. Additional eligible completed device reports retain individual backup/retry controls; there is no bulk import dialog. Shared pure parsers validate browser and cloud snapshots; exact-set grading, legacy optional metadata, title presentation and all reviewed content remain unchanged. Only completed, valid reports are uploaded after successful local submission. Cloud failures never gate local submission.

Cloud report writes pass through authenticated Edge Functions and a restricted SQL transaction. Owner/attempt uniqueness plus a versioned canonical content hash makes matching retries idempotent and rejects conflicting overwrites. RLS/grants limit reads to the account owner and deny browser report writes. Deletion strips payloads into tombstones so old requests cannot recreate them. Account deletion requires the current password and cascades account records.

Device originals stay in their existing localStorage keys. Separate ownership markers preserve account isolation even when IndexedDB queue/cache bookkeeping is cleared. Uploads are bounded, retry transient errors, and can be paused/resumed; pending jobs never change owner. Sign-out/switch invalidates late responses, hides private originals and clears downloaded account copies. Guest originals remain independent.

Account history loads metadata in pages of 20 and downloads full reports on demand into the existing read-only Results/PDF renderer. Verified matching local/cloud reports appear once across the device/account sections. Optional trusted-device downloads include validated metadata/payload for offline use. They are separate from original writable attempts. Export is available only for individual Results reports as PDF; device-copy removal first verifies a matching cloud backup.

## Optional usage analytics

PostHog analytics is enabled only with `VITE_POSTHOG_ENABLED=true` and a browser project token/API host. The SDK loads separately and telemetry failures cannot gate authentication, exam saving, expiry, submission, backup or PDF export. Virtual pageviews distinguish Start, Exam, Results and Account settings. Accepted Supabase sessions use the account UUID; restoration/token refresh are activity rather than explicit login events, and logout/account switches reset attribution. Successful start/resume, saved completion/expiry, review opening, PDF-download initiation and confirmed report backup emit allowlisted metadata. Reopening a completed report is not another completion. Completion transitions are checked within the existing shared Web Lock; attempts/snapshots/grading are not changed for analytics.

Estimated active time counts visible, focused use until five minutes after an input/focus return, with periodic increments and old-context flushes before changing view/account. Hidden/unfocused time and execution gaps over 15 seconds are excluded. It differs from elapsed exam time and built-in session duration. Raw question/report content, emails and auth tokens are excluded; SDK public project-token fields needed for ingestion are retained, while URL query strings/fragments and sensitive initial person properties are scrubbed. DOM autocapture, recordings, heatmaps, automatic exceptions and performance capture are disabled. Analytics is best effort; Supabase remains authoritative for registered-account counts. Configuration, dashboard definitions and operational limitations are in [POSTHOG_SETUP.md](POSTHOG_SETUP.md).

## Responsive and accessible interface

Use a centred reading column, light neutral background, white cards, subtle borders, one teal accent, and readable sans-serif text. Shared container, card, button, Markdown, and dialog primitives are responsive from 320px upward. Body text is about 16px, controls target at least 44px, focus is visible, text and URLs wrap, and page-wide horizontal scrolling is avoided. Tables may scroll inside labelled containers. Dialog content scrolls within the viewport while actions remain reachable. Support touch, mouse, keyboard, portrait and landscape, safe areas, and enlarged text. Viewport changes must not reset answers, flags, timer, or question position.

Across the four views: stack exam details and history on narrow screens; keep timer, progress, answer cards, and all navigation actions accessible; adapt the review grid and show answered, consolidated unanswered, flagged, and remaining-time details; stack results and domain summaries, wrap filters, and keep expanded explanations and source references readable.
