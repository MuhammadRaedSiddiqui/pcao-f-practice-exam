## 2. Resolved conflicts and design decisions

| Older proposal or ambiguity | Approved resolution and reason |
| --- | --- |
| Optional routing / three views | Extend the installed router and AppView; keep App mounted. Avoid a second independent view coordinator. |
| Frontend-only means no account/analytics functionality exists | Guided needs neither, but existing optional services remain intact. No guided cloud sync, new telemetry, SQL, Edge Functions or account requirement. |
| Suggested localStorage namespace | Use a **separate IndexedDB database** through installed `idb`. Frozen content consumes significant space; existing localStorage already has documented quota pressure. Transactions avoid a second record/index rollback scheme. Keep shared Web Lock for interoperation with Mock creation. |
| Guard only the visible Exam view | Guided gate scans **all** saved attempts in the origin, including inaccessible owners, while revealing no private details. Leaving Exam does not make its running deadline disappear. This is intentionally stricter than account controls' view-based exam restriction. |
| Phase 3 refresh acceptance precedes Phase 4 persistence | Phase 3 is a development-only in-memory UI milestone with minimum gate already integrated. Durable refresh acceptance belongs to Phase 4; no Phase 3 public release. |
| Three hint states plus answering | Store monotonic hint count orthogonally to answer phase; avoid an unnecessary combinatorial state machine. |
| Example `Q01` / reviewStatus is enough approval | Actual IDs are `Q1` etc. Require release allowlist digests plus editorial ledger; a JSON string saying approved cannot itself publish content. |
| Unknown historical difficulty | Infer only from exact recognized examId/version and matching snapshot fingerprint if metadata is missing. Conflicting explicit difficulty makes the item unavailable. Never infer from title, shared Q ID, option similarity or question position. |
| “Previously reviewed” implies actual exposure tracking exists | No such history exists. Label **all post-exam retries** “Answers may already have been seen”; standalone repeat claims remain conservative. No mastery claims. |
| Advanced “enough for coherent release” | Set the Phase 8 default release gate to all 60 reviewed Advanced items. A smaller release requires a separately approved coverage change. |
| Phase 6 includes deployment proof | Separate local release readiness, deployment authorization, and production acceptance. Passing local QA never authorizes deployment. |

## 4. Exact source binding and publication

Proposed TS sketches are contract pseudocode, not committed source or production content:

```ts
type SourceIdentity = {
  schemaVersion: 1; examId: string; bankVersion: string;
  difficulty: 'intermediate' | 'advanced';
};
type Fingerprint = `sha256:q1:${string}`; // exactly 64 lowercase hex after prefix
type SourceBinding = SourceIdentity & {
  questionId: string; sourceFingerprint: Fingerprint;
};
```

Fingerprint algorithm q1: operate on the **successfully validated source** (bank loader for standalone; parseAttempt/validated cloud payload for reports). No additional trim, newline normalization, Markdown rendering, Unicode normalization or sorting of arrays. Serialize this fixed-position tuple with JavaScript `JSON.stringify`, UTF-8 encode, SHA-256 using `crypto.subtle`, format lower hex:

```ts
[
  'pcao-f-guided-question', 1,
  source.schemaVersion, source.examId, source.bankVersion, source.difficulty,
  [domain.id, domain.title, domain.expectedQuestionCount],
  question.id, question.primaryDomain, question.selectionCount,
  question.stemMarkdown,
  question.options.map(o => [o.id, o.textMarkdown]),
  question.correctOptionIds,
  question.explanationMarkdown,
  question.options.map(o => [o.id, question.optionExplanations[o.id]]),
  question.sources.map(s => [s.courseTitle, s.sectionHeading, s.url ?? null])
]
```

Object insertion order never affects this tuple; order of options, correct-ID array and sources deliberately does. Domain metadata is bound. Changing any pedagogically relevant field or source version rejects an old guide, even if only one field changed. File formatting is separately protected by byte hashes. Bank validation trims text, so q1 identifies the exact validated/frozen representation, not whitespace around raw JSON strings. Test this distinction explicitly. Golden vectors must be written in Phase 1 with independently calculated expected hashes (not generated by the function under test); compare Web Crypto with Node SHA-256 in unit tests, then repeat the vectors in a real browser in Phase 3/6. Reuse no existing `reportHash` because it has a different normalization/domain purpose. If Web Crypto is unavailable, show unsupported guidance, never a weaker fallback hash.

### Overlay contract

Apply string length/collection bounds (below), uniqueness and membership refinements. The JSON contains exactly:

A release SHA-256/r1 may be retained as a transport/artifact check; it is not a third approval authority or separate workflow. Compute g1, and optional r1 if used, with one small guided-only canonical JSON serializer: recurse through JSON values, sort object keys by JS code-unit comparison (`a < b`), preserve arrays, serialize primitives with JSON.stringify, accept no undefined/nonfinite numbers. ## 5. Eligibility and deterministic selection

`resolveEligibility(source, release, optionalReportFilter)` returns ordered matched source questions, eligible pairs, and excluded counts by typed reason. Identity requires schemaVersion, examId, bankVersion, difficulty AND fingerprint equality. No fallback matching.

D12 policy approved by the owner in the targeted Phase 6 authorization; implemented as follows. Standalone pilot remains Intermediate only, default length 5, alternative 10. For n verified eligible items and size s, disable s when n<s; otherwise offer ceil(n/s) sets. Zero-based set j uses start=min(j*s,n-s), end=start+s (exclusive). All sets contain exactly s unique questions in eligible source order; only a final remainder set overlaps. Repeated count is zero for j=0, otherwise max(0,j*s-start). Set labels and a wrapping selected-set description disclose ordinal, eligible range and repeated-question count. For n=11, size5 ranges are 1–5, 6–10, 7–11 (4 repeated); size10 ranges are 1–10, 2–11 (9 repeated). Ten/sixty item partitions remain disjoint. Test exact cardinality, no internal duplicates and complete eligible-item union. No randomization, adaptive rotation, silent shortening or cross-source substitution.

Revoked and exact-source mismatched entries are excluded from new sets after strict source/release/catalog integrity validation; unapproved, unsupported or structurally invalid data cannot supply items. Changing length resets setIndex to0. If refreshed coverage invalidates the chosen index, disclose that choice as unavailable and require an explicit valid selection; do not silently select a replacement. Frozen sessions retain their original item membership/answers/hints/commitments under current exact approval/access checks, including when new sets of that size are disabled. A revoked item inside a frozen session keeps the record preserved and instruction inaccessible. Post-exam cohorts are unchanged. Domain practice and Advanced expansion remain later owner decisions.


Store only the selected question subset and guide entries; no full 60-question bank per five-question session, no original exam answers/score/email/tokens. A subset is **not** a QuestionBank: never pass it to the existing full 60-question validator. A new strict subset schema mirrors Question; compile-time assignability/parity fixtures must detect drift with the exported `Question` type. Validate source parent before selection and every subset field on recovery, including IDs/domain/option explanations/sources, fingerprints and approved guide digests. Deep-clone/freeze immutable items. Bound sessions to 60 items and ≤4 MiB encoded JSON; resource failures produce explicit messages, never truncate content.

Session validation requires UUID IDs/commands, safe integer revision ≥0, valid finite integer date timestamps, `updatedAt >= startedAt`, commitment timestamps within start/update, no response for unknown items, exactly one response per item, known unique selected IDs and count ≤selectionCount, index within items. Standalone requires nonnegative integer setIndex and items.length===selectionSize; creation revalidates the selected complete set against current eligible source order. Completed requires all items committed and completedAt between start/update; incomplete has completedAt=null. Recompute correctness from committed exact set; **do not persist authoritative isCorrect/score**. A committed response must have exact cardinality. Cross-record immutable fields (origin/source/items/start/id/guideVersion) cannot change during writes; committed selection/time/command and revealed hint maximum never regress. Session clocks are bookkeeping, not timers; normalize writes with `max(now, updatedAt)` after backward clock adjustments.

Commands: `select(questionId, ids)`, `revealNextHint(questionId)`, `navigate(index)`, `commit(questionId, commandId)`, `finish(commandId)`. All include expectedRevision at storage boundary. Selecting a radio replaces the prior answer; Clear empties an uncommitted answer. Checkboxes toggle with a cap; a cap says nothing about correctness. At commitment require exactly N distinct valid options, run `isExactSet`, and lock the first successful saved answer. Repeat of the same commitment (including a lost acknowledgement) returns the current committed record without a revision increase. Any later alternate commitment or selection is rejected, not treated as another attempt.

Hints are optional: answering has `maxHintRevealed=0`; each explicit reveal increments by one to 3, never skips. Collapse/reopen is ephemeral visibility only and cannot reset the recorded maximum. No new hint requests after commit; show already requested hints and the full feedback instead. UI does not expose correct IDs, explanations, option comparisons, decisiveCriteria, glossary/source detail or correctness markers in **any** precommit rendering branch or accessibility attributes. Pass a restricted precommit view model containing only question stem/options/count and already-revealed hint strings. Full data exists in client resources; this protects ordinary experience, not deliberate resource inspection.

Persist all commands before treating their effect as saved. Draft answer feedback may be optimistic with an explicit pending indicator; do not expose a new hint or feedback until successful save. If save fails, roll back pending visual selection to committed state and keep Check answer unavailable until reconciliation. Stale command reloads latest record and asks the learner to retry; never silently merge/auto-resubmit. No opportunistic answer scoring while choosing.

Next/Previous may visit any selected question. Uncommitted drafts survive navigation; users must commit every item before Finish is enabled. Last commitment does not silently navigate away from feedback; Finish records completed status once. Completed sessions are read-only; repeating creates a new ID with a conservative exposure label, never unlocks the old answer.

Summary: committed correct/committed count (and total session size), correct-without-hints count/committed count, total hints requested, and items to revisit. Correct-without-hints means hints=0 for that guided retry; it does not establish unseen mastery. Post-exam always carries exposure notice. No pass/fail, timer, predicted readiness, certification percentage or combined Mock/Guided score.

## 7. Storage, recovery and cross-tab protection

Dedicated IDB database `pcao-f-guided`, database version 1, object store `sessions` with keyPath `id`. Record schemaVersion is independent of IDB version, fingerprintVersion and guideVersion. No shared archive DB, Mock index, ownership marker or backup-queue entry. Small pilot needs no separate writable history index; derive visible session summaries from validated records, hiding private ones before display. Per-item validation error must not suppress unrelated valid sessions. Explicit session removal deletes only that guided key after a clear confirmation; no automatic eviction of Mock or guided records.

Use the existing origin Web Lock for guided commands that check Mock state, then a short IDB readwrite transaction: read latest, expectedRevision/idempotency/immutable checks, put entire next record, await transaction completion. IDB transaction is the atomic durability point. Initialize/open/validate the DB and compute hashes/freeze before acquiring the Web Lock. Under the lock perform only the fresh source/protection check and short transaction; never wait for network, DB initialization or digest work there, and never perform unrelated awaits inside an active IDB transaction. ### Active Mock gate

Approved D7–D9 contract: `MockGate = checking | clear | blocked | recovery-required | unsupported`, with discriminated reasons and nonsensitive index diagnostics. `checking` is transient and bounded; access failures or a checking timeout become explicit Retry/recovery states, never indefinite loading. Under the existing shared lock, read the index and enumerate **all exact** `pcao-f:attempt:v1:` keys. Do not modify the index, records or ownership markers. Storage/record failures take precedence as recovery-required; otherwise any validated live record produces blocked; otherwise clear may carry a malformed/stale-index warning. Unsupported coordination capability fails closed with an explicit unsupported state.

| Observed state | Protection result / allowed action |
| --- | --- |
| Valid indexed or orphaned unfinished record, now < verified deadline | Block all guidance, regardless of owner; ordinary Resume only if the learner has source access. |
| Fully validated unfinished record, now >= verified deadline | Does not block standalone; does not become an eligible submitted source report. Other live or unreadable records still block. |

| Dangling indexed ID with no record, complete validated inventory otherwise | Missing record alone is not a live attempt; retain stale-index warning without repair. |
| Corrupt/unreadable/unsupported-format attempt record, incomplete enumeration, storage denial or scan timeout | recovery-required with typed reason (for example corrupt-record, unreadable-record, incomplete-inventory or storage-unavailable); fail closed and offer Retry. | Valid submitted records only, or no present records | clear, subject to independent source/ownership/content checks. |

Other valid live records or corrupt/unreadable inventory still prevent clear. App may independently finalize through its existing flow; Guided never calls or waits on a Mock finalizer to unlock standalone, and never submits, regrades, replaces or repairs an attempt.

Approved D9 recovery requirements: define typed failure reasons, finite checking, explicit Retry, privacy-safe explanations and an ownership-checked user-controlled recovery contract in Phase 1. Preserve original bytes, distinguish storage/index/record failure, revalidate the entire inventory after recovery and never offer a bypass based on a guessed expiry. Do not silently delete/quarantine/overwrite records, repair the Mock index or export another owner's raw data. Any workflow needing Mock-facing data changes requires its own explicit approval; Guided approval grants none. ## 8. Compatibility and release controls

Roll back to a build retaining guided schema/catalog support when possible; if an older build lacks routes, Home fallback must preserve IDB data. Production deploy/rollback each require explicit owner authorization. There is no remote switch/backend/API in this design; flag changes require an authorized rebuild/redeploy.

Rollback runbook: identify defective source/build/guide digests and stop promotion; prepare a reviewed disabled-Guided artifact or last compatible artifact with still-approved catalog entries; add an explicit revoked digest if content itself must be withdrawn; obtain owner approval of that exact artifact/host; deploy only after approval; smoke-test Mock start/resume/submission/ordinary reports plus disabled guided direct routes and untouched IDB records. Do not clear origin storage or rewrite Mock reports to roll back. Record actual host/assets and remaining saved-session limitations, then obtain separate approval for a repaired release. If a pre-Guided artifact lacks new route rewrites, retain compatible routing in the rollback artifact or document/test safe Home fallback before approval.

Deferred choices with no permission implied: owner/editor identities, course access and reviewer availability, final ten IDs, learning-observation recruitment, actual production artifact/hostname, and future execution/deployment authorizations. The Phase 0/0-B isolated baseline method is accepted; future checks require the applicable phase scope. Defaults and decision deadlines are in the [master plan](GUIDED-PRACTICE-MASTER-PLAN.md).
