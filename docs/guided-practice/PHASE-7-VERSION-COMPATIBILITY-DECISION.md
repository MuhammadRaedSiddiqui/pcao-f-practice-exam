# Phase 7 — Guide-version compatibility recommendation

2026-10-18. **Recommendation only; no version, guide, approval, catalog, session or runtime changed.** Phase 7 is incomplete. See the [educational audit](PHASE-7-CONSOLIDATED-EDUCATIONAL-AUDIT.md) and [owner packet](PHASE-7-OWNER-REVIEW-PACKET.md) for the separate educational decisions.

Recommend a uniform **1.1.0 release for new sessions**, once separately reviewed and authorized, while retaining the existing **1.0.0 pilot identities and their exact validation path for old frozen sessions**. Rebind the ten unchanged pilot entries to new 1.1.0 g1 values through an explicit owner decision; do not rewrite their existing records or stored sessions. This keeps the current algorithms, release/session schemas and persistence model intact. It does not extend the pilot waiver to the fifty new guides.

## Options compared

### A. Uniform 1.1.0 for new work; retain 1.0.0 for frozen history — recommended

**Changes needed later:** generate the separately approved sixty-entry immutable 1.1.0 artifact and its exact map; retain a distinct compatible 1.0.0 catalog row/map and, where authorized, its immutable ten-entry artifact. Put the current 1.1.0 row last for the same source. Existing schemas, q1/g1 functions, sessions and storage need no redesign. This is future data/catalog integration, not work implemented here. A source/version/path mapping and enabled-build decision still require review.

**Approvals and g1:** fifty new guides already target 1.1.0, so their present prospective identities remain usable if content/review IDs do not change. Each pilot entry receives a different g1 under 1.1.0 even with identical entry bytes. Keep its original 1.0.0 acceptance intact; obtain an explicit exact-digest owner decision for the new 1.1.0 binding. The owner must also state whether the original ten-only waiver covers this unchanged-prose, version-only reuse or whether additional pilot review is required. Nothing here grants that decision or excuses independent human review of any new guide.

**Saved sessions and feedback:** old sessions continue under 1.0.0 with their exact items, reveals, commitments, index and feedback. New sessions use 1.1.0. Historical feedback is not replaced by current-release prose. A missing old public file can be compatible with an already complete frozen session if its retained source/version/map still authorizes every item; it prevents starts that need that file and is not a reason to remove its catalog identity. This is a code-path inference requiring the regression cases below, not a new demonstrated compatibility result.

**Revocation/source:** retain exact source identity and separate maps. If a defect affects a logical pilot guide in both versions, assess and explicitly revoke both corresponding g1 lineages where necessary. A revocation in one version is not automatically global. Never leave an unsafe digest authorized merely to make resume appear successful; preserve data and show the existing blocked/recovery behavior instead.

**Regression and rollback:** prove old-version resume and new sixty-item coverage together. Roll back selection/build behavior while retaining authorization for safe 1.1.0 frozen sessions. Reordering the retained 1.0.0 row to last would select old coverage for fresh starts; retaining the 1.1.0 row earlier can still permit saved-version validation. A build/catalog rollback that drops the 1.1.0 row would strand those sessions and is not a compatible rollback. If unsafe content requires withdrawal, explicitly accept the resulting unavailable sessions rather than silently migrating them. Preserve the compatible reader, maps and approved assets in the rollback package.

### B. Publish all sixty at 1.0.0 — possible only with a plan amendment; not recommended

**Changes needed:** amend the accepted full-release target from 1.1.0, regenerate fifty expansion version bindings/maps and designate a first-publication artifact/path. No existing public 1.0.0 file may be overwritten. Because production is empty, a first-publication 1.0.0 package could in principle be authorized; this does not authorize replacing the accepted local ten-entry artifact or silently changing its meaning.

**Approvals/g1:** the original ten g1 values can remain exact if their entries/source stay unchanged. All fifty expansion g1 values change from their current planned-1.1.0 values, although unchanged draft-entry SHAs/q1 values do not. Their review materials and eventual approvals must bind those new version values. New-guide human requirements remain intact.

**Sessions/revocation:** old and new frozen items can validate against one same-version approval map containing the sixty exact digests. Source rules and per-digest revocation remain unchanged. However, the current catalog permits only one row per source/version. It cannot retain separate ten- and sixty-entry maps at the same key, and a ten-entry file fails published validation against a sixty-entry map. Thus the same version would describe different coverage generations without a clean selection boundary.

**Tests/rollback:** test same-version coverage evolution and all old frozen entries, plus the effect of map changes on every new session. Reverting that row to a ten-entry map makes fifty-entry sessions unapproved; keeping the sixty-entry map while serving the old ten-entry file fails the length contract. Compatible rollback needs another version, a separately designed selection mechanism, or explicit suspension of affected starts. This increases ambiguity and abandons the agreed 1.1.0 milestone to save only ten version bindings.

### C. Preserve all current digests through a composite, multi-version catalog/session — technically viable redesign; not recommended

Keep the ten pilot entries as 1.0.0 and fifty new entries as 1.1.0, then introduce an explicit composition manifest and per-item version-aware validation. Existing q1/g1 algorithms could remain unchanged when called with each item's own version; the present release/eligibility/session contracts cannot express that composition.

**Changes:** add versioned composition/loading/coverage contracts, per-item source-version-digest references and a compatible new session format/reader; revise approval resolution, selectors, persistence validation, revocation propagation and error reporting. Retain the old session reader. Do not mutate old sessions to satisfy the new format. A pair of unmodified existing releases alone is insufficient: current runtime selects one row, so it yields ten or fifty, not sixty, and cannot create a mixed-version current-format session.

**Approvals/g1:** current entry g1 values can be retained, but the owner must authorize the composition and its exact membership plus all fifty educational approvals. Old pilot acceptance remains confined to those old identities; it does not approve the composed release behavior. Revocation must follow the referenced version/map and handle lineage explicitly.

**Tests/rollback:** a broader matrix must cover mixed versions within each 5/10 session and each post-exam filter, legacy reads, composition tampering, version confusion and withdrawal. New-format sessions would not be readable by an old-format rollback build unless that build retained the new reader. This adds storage/runtime/release obligations for no educational benefit to these unchanged entries and conflicts with the Phase 7 plan's additive, same-schema approach unless separately amended.

### Invalid shortcuts

Do not put the ten 1.0.0 digests into a 1.1.0 approval map and expect unchanged prose to validate: recomputation yields different g1 values. Do not omit guideVersion from g1, accept multiple arbitrary digests for an ID, bypass revocation, or rehash existing sessions to the current version. Do not label the new full version 1.0.0+full to preserve g1: the exact version string participates in the hash, including metadata. These are not compatible uses of the current contracts.

## Required future evidence for option A

These are proposed tests, **not executions in this documentation pass**:

1. Recompute all sixty exact q1/g1 values under the intended full version; reject stale digests, missing/extra options, unreviewed entries, wrong source tuples, duplicate IDs and wrong version/map/path combinations.
2. Confirm that current selection uses the intended last source-matching row, while the retained 1.0.0 row remains resolvable by exact version. Test deliberate row-order reversal and separate source versions/difficulties; no silent fallback or source conflation.
3. Freeze representative old sessions at each hint/commitment/navigation state; compare full items/source/version/responses/index before and after rollout, reload, cross-tab recovery and completion. Test missing old public asset with intact frozen content/map, and missing/revoked map without destructive overwrite.
4. Verify all 60 eligible Intermediate entries, twelve five-item and six ten-item sets, exact final overlap rules, all domains and select-one/two/three commitments. Verify All/incorrect-unanswered/flagged report cohorts against their frozen original reports, including exact-source mismatches.
5. Verify explicit old/new digest revocations, both-lineage withdrawal when applicable, and non-destructive unavailable/recovery handling. Re-addition must require a deliberate authorization, never happen through a new catalog order alone.
6. Exercise a compatible rollback with both version readers/maps/assets retained where safe. Validate new-session selection and both generations of saved feedback separately; never equate rollback with deleting newer approvals or replacing frozen prose.
7. Complete applicable storage/ownership/Mock/Results/PDF regressions, release/resource/fault/readability/native-accessibility and physical-device/browser obligations, then authorized hosting smoke and rollback acceptance. Preserve historical PDF/recovery/timing/resource-pressure evidence and the sequential one-worker browser direction.
